# 10 · 学习成长机制

> 作者：大脑（Claude）　日期：2026-10-30
> 目标：每批新资料进来，系统都比上一批更准、需要人工复核的量更少，而且**不会学到错的东西**。
> 基础：沿用 `QuoteStandardizer/ERROR_CODES.md` 已有的错误码、人工裁决（verdicts）、回归用例（fixtures）、修复账本，本文件在其上补全“知识积累、样本挑选、防错学习、成长度量”四部分。

## 0. 先说清楚“学习”是什么

我们用的视觉模型（Gemini CLI、DeepSeek）**不会因为看过我们的资料而变聪明**，它们的参数不会改变。所以“学习”指的是**系统**在积累，具体落在四个地方：

| 积累在哪里 | 内容 | 例子 |
|---|---|---|
| ① 标准答案集 | 人工对照原件核实过的事实 | 某份报价单每一行的名称、规格、单位、单价 |
| ② 知识库 | 可复用的通用规律（数据文件，不是代码分支） | “报价城市”是地区列；“㎡”等同“m²”；“例:”开头的行是示例 |
| ③ 回归用例 | 曾经出过错的场景，永久保留 | 褪色的“4”被读成“1”的那一页 |
| ④ 代码规则与提示词 | 需要改逻辑才能解决的问题 | 矩阵表判定条件、切块逻辑、转录提示词 |

**唯一允许的学习来源是“人工对照原件核实过的事实”**。模型输出、程序输出、第三方解析结果，都不能直接成为学习材料。这一条防止“模型教模型”的循环（上一轮白皮书评差和第 1 批标准答案集都栽在这里）。

## 1. 每批新资料的成长循环

```
新资料进来
 │
 ① 入库登记 ─── 计算 sha256、去重、分类（文件类型、表格形态、是否扫描、是否盖章、页数）
 │              新出现的“形态组合”标记为【新类型】
 │
 ② 当前版本盲跑 ── 用当前代码原样处理整批，记录代码版本号
 │                 ★ 这一步的准确率 = 系统对“没见过的资料”的真实能力（首测成绩）
 │
 ③ 挑选核实样本 ── 按第 3 节的规则挑出要人工核实的文件与单元格
 │
 ④ 人工核实 ───── 只看原件，转录真值（03 规程 V2–V3）
 │
 ⑤ 三方裁决 ───── 真值 / 我们 / 线上 逐格对齐；每处差异判定 + 错误码（ERROR_CODES.md）
 │
 ⑥ 提炼学习项 ─── 每条“我们错”的差异，按第 4 节决定学成哪一种：
 │                知识库条目 / 回归用例 / 代码工单 / 提示词改动
 │
 ⑦ 验证学习项 ─── 新知识或新代码必须在【全部】回归用例 + 本批真值上通过门禁，
 │                且不能让任何旧用例变差（不退步）
 │
 ⑧ 发布新版本 ─── 提交、打版本号、更新知识库版本、写成长记录
 │
 ⑨ 复测 ──────── 用新版本重跑本批，记录“学习后成绩”；下一批的首测成绩才是真正的进步证明
```

每一批都留下两份成绩：**首测成绩（学习前，对新资料）**和**学习后成绩（对本批）**。只有首测成绩持续提高，才说明系统真的在成长；学习后成绩高只说明“记住了这批”。

## 2. 知识库（新增）

### 2.1 位置与形式

`QuoteStandardizer/knowledge/`，纳入 git 版本管理，每类一个 YAML 或 CSV 文件，代码启动时加载：

| 文件 | 内容 | 现在散落在哪里 |
|---|---|---|
| `header_synonyms.yaml` | 表头同义词：哪些表头表示单价、单位、地区、品牌、名称、规格 | `main.py` 的 `REGION_HEADER_KEYS`、`llm_agent.py` 的 `UNIT_PRICE_KEYS` 等 |
| `unit_aliases.yaml` | 单位等价写法 | `main.py` 的 `UNIT_ALIASES`、`evaluate.py` 的等价表 |
| `row_patterns.yaml` | 非物料行的特征：合计、小计、示例行、签章行、页脚 | `main.py` 的 `SUMMARY_ROW_KEYS` 等 |
| `terms_phrases.yaml` | 商务条款常见表述与归一（付款方式、运费、税率、折扣写法） | `terms_extractor.py` |
| `layout_patterns.yaml` | 表格形态识别特征（矩阵表、左右并排、跨页续表、旋转） | `main.py` 的 `_detect_matrix` 判据 |
| `prompt_examples/` | 提示词示例库：从真值中挑选的难例（见 2.3） | 尚无 |
| `category_codes.csv` | 标准分类编码（由用户提供） | `CATEGORY_CODE_FILE` |

### 2.2 每条知识的格式

```yaml
- id: HDR-REGION-0007
  rule: "表头含“报价城市”视为地区列"
  status: active            # candidate / active / retired
  evidence:                 # 必填：来自哪份原件、哪一格，截图路径
    - sample: "东莞市亮美聚光电科技有限公司"
      location: "第1页 表头第8列"
      screenshot: "fixtures/.../evidence/xxx.png"
  regression: "fixtures/.../亮美聚"   # 必填：对应的回归用例
  added: 2026-10-30
  approved_by: 大脑
  notes: ""
```

### 2.3 提示词示例库
- 只从**已核实真值**中挑选难例（公章遮挡、褪色、合并单元格、旋转、矩阵表等），每个示例保存：页面截图、正确转录、为什么难；
- 示例中的供应商名称、价格等具体内容必须替换为中性占位（防止被模型抄进输出，违反 I9）；
- 运行时按“表格形态”挑选最相近的 1–2 个示例放入提示词；示例库变动和代码改动一样要过回归门禁。

### 2.4 知识的三种状态
- **candidate（候选）**：执行者从差异中提炼出来，附证据，尚未生效；
- **active（生效）**：大脑审核通过，且全部回归用例通过；
- **retired（退役）**：发现会导致误判时退役，保留记录不删除，并写明退役原因与反例。

## 3. 挑选核实样本（让人工花在刀刃上）

人工核实是成长的唯一燃料，但人力有限，按以下优先级挑选：

| 优先级 | 挑什么 | 比例 |
|---|---|---|
| 1 | **新类型**文件：前 3 份全文件核实 | 100% |
| 2 | 程序标了“待人工复核”的格子 | 全部 |
| 3 | 识别流水线中“读数分歧经裁决采用”的格子（`08` 第 4 节） | 全部 |
| 4 | 我们与线上结果不一致的格子 | 全部 |
| 5 | 程序认为完全一致、无任何标记的文件：**随机哨兵抽检** | 每批至少 10% 的文件，每份至少 10 格 |

第 5 条是发现“两边同错、程序也没察觉”的唯一手段，**永远不能降到 0**。

**信任分级**：每种文件类型按其历史首测成绩分级，抽检比例随之调整：

| 级别 | 条件 | 哨兵抽检比例 |
|---|---|---|
| 新类型 | 核实文件 < 3 份 | 100% |
| 观察 | 连续 3 批首测漏报为 0 | 30% |
| 稳定 | 连续 5 批首测漏报为 0，且整单合格率 ≥ 95% | 10% |
| 降级 | 任一批出现漏报 | 立即回到“新类型”级别 |

## 4. 一条错误该学成什么

| 错误性质 | 学成 | 判断方法 |
|---|---|---|
| 某种写法没认出来（表头叫法、单位写法、条款措辞） | 知识库条目 | 只需补一条同义/等价关系就能解决 |
| 某种版式没处理好（矩阵、跨页、旋转、并排） | 代码工单 + 布局知识 | 需要改解析逻辑 |
| 视觉模型读错（褪色、公章、小字） | 回归用例 + 提示词示例 / 增强参数调整 | 原件有一定识别难度 |
| 程序没把存疑标出来（漏报） | **新增自检规则**（`04` 第 6 节漏报专项） | 值错了但没有任何待复核说明 |
| 标准答案本身错了 | 修正标准答案（走 `04` 第 2.4 节争议流程） | 回到原件确认 |
| 原件本身看不清 | 不学；记录为“原件无法判定” | — |

每一条“我们错”的差异，都必须落到上表某一行；不允许“已知但不处理”。

## 5. 防止学到错的东西

1. **来源约束**：知识条目、回归用例、提示词示例的 `evidence` 必须指向原件截图；没有证据的条目不得生效。
2. **通用性约束**：禁止针对某个文件名或某家供应商写规则（沿用 ERROR_CODES.md 约束 1）。新规则至少要在 2 家不同供应商的资料上成立，否则只登记为候选。
3. **不退步约束**：任何学习项生效前，必须在全部回归用例上通过；有一个旧用例变差就不得生效。
4. **可回滚**：知识库与代码都在 git 中，每个版本都可回退；成长记录写明每个版本引入了哪些学习项。
5. **历史画像只报警不填值**：可以记录某供应商历史上的版式、价格区间，用于发现异常（例如“这家以前都是矩阵表，这次判成清单表”），**但绝不能用历史数据填写或改动本次的任何值**。

## 6. 成长度量

每批写一行到 `codex/代码处理/QuoteStandardizer测试/成长记录.csv`：

| 字段 | 说明 |
|---|---|
| 批次、日期、代码版本、知识库版本 | — |
| 文件数、新类型数 | — |
| **首测**：整单合格率、字段准确率、漏报数 | 学习前，对新资料 |
| **学习后**：整单合格率、字段准确率、漏报数 | — |
| 人工核实工作量 | 核实的文件数、格数、耗时 |
| 新增：知识条目数 / 回归用例数 / 代码工单数 | — |
| 复发数 | 本批错误中，属于“以前修过的同类错误”的条数 |

判断系统在成长的标准：
- 首测漏报数稳定为 0；
- 首测整单合格率逐批上升；
- 每批需要人工核实的格数逐批下降（在哨兵比例不降的前提下）；
- 复发数趋于 0。

任一指标连续两批变差，大脑必须做专项复盘。

## 7. 节奏与分工

| 时点 | 动作 | 负责 |
|---|---|---|
| 每批新资料到达 | 执行第 1 节 ①–⑨ | 执行者；人工核实由用户安排或执行者按规程转录 |
| 每批结束 | 审核学习项（知识条目、代码工单、提示词示例）；批准发布 | 大脑 |
| 每 4 批或每月 | 复盘成长曲线；调整信任分级与抽检比例；清理退役知识 | 大脑 |
| 业务规则变化 | 例如输出规范、地区写法、编码库更新 | 用户决定，大脑落地为知识或工单 |

## 8. 落地工单（第 4 批，在第 3 批 E0–E3 完成后执行）

| 工单 | 内容 | 验收 |
|---|---|---|
| L1 知识库外置 | 把散落在代码里的表头同义词、单位等价、非物料行特征、条款措辞迁移到 `knowledge/` 下的数据文件，代码改为加载；行为不变 | 迁移前后全部回归用例结果完全一致 |
| L2 知识条目格式与校验 | 按 2.2 节格式；启动时校验每条 active 条目都有 evidence 与 regression，缺失则拒绝启动 | 构造缺证据条目，程序拒绝启动并指出条目 id |
| L3 入库登记与新类型识别 | 新批次自动登记（sha256、去重、形态分类），与已有形态对比标记新类型；生成本批核实样本清单（第 3 节规则） | 用 `正式样例库清单.xlsx` 的两个目录试跑，输出新类型清单与样本清单 |
| L4 成长记录 | 每批首测、学习后两份成绩写入 `成长记录.csv`；复发数自动统计（按错误码 + 根因归类） | 用已完成的批次补录一行 |
| L5 提示词示例库 | 建立 `prompt_examples/`，从已核实真值中选首批 5 个难例（占位化），按形态检索注入；过回归门禁 | 开启前后在回归用例上对比，准确率不下降 |
| L6 信任分级 | 按第 3 节维护每种文件类型的级别与抽检比例，写入每批样本清单 | 构造一批含漏报的结果，确认对应类型自动降级 |
