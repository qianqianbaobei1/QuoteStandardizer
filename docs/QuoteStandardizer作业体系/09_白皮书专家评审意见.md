# 专家评审意见：《建材报价单标准化解析与全参数评差技术白皮书》

> 评审人：大脑（Claude）　日期：2026-10-30
> 评审对象：`~/Desktop/四人建材报价标准解析与评差全量汇总/建材报价单标准化解析与全参数评差技术白皮书_专家评审专供.md`
> 及同目录交付物（评差总表、本地标准解析成果、原始文件与线上解析档案）、评差脚本 `QuoteStandardizer/generate_evaluation_report_v2.py`

## 一、评审结论

**方向正确，核心结论不成立，现状不可提交专家评审。**

白皮书的方法论框架（单份零差异口径、输入隔离、缺陷编码、逐行证据台账、三份档案并存）值得保留；但它的核心数据“线上系统全参数合格率 11.4%（117/132 家不合格）”是以**未经核实的本地程序输出**为“真值”计算出来的，且评差脚本存在会制造假缺陷的配对与比对错误。在完成第四节的整改之前，该数字不能对外报告。

## 二、致命问题（经核实）

### 1. “绝对真值”就是本地程序自己的输出

| 证据 | 位置 |
|---|---|
| 评差总表中“原表有效行数”与“本地自跑行数”在 **132/132** 家完全相同 | `四人全景评差与缺陷归因总表.xlsx` 四个分表 |
| 代码直接把本地行数赋给“原表行数”：`src_rows = local_rows  # 本地验证过的有效物料行数即为真实基准` | `generate_evaluation_report_v2.py` 第 120 行 |
| 本地评定在代码中写死为 `"PASS"`（第 152、165、323 行）；交付表中本地 129 家 PASS、3 家 SKIP，无一 FAIL | 同上 |
| 全部比对（行数、单价、单位、规格、条款、税率）都是“线上 vs 本地”，没有任何一项回到原件 | 同上第 167–318 行 |

白皮书第五章案例 2 批评周伟批次“自己批改自己的试卷”，但整套评差把本地模型当作标准答案去判线上模型，本质上仍是“用一个未经核实的模型去判另一个模型”。本地程序本身会出错（本项目此前实测：视觉模型把褪色的 400000 读成 100000；由模型输出整理出的“标准答案”带着同样的错误且标为“清晰”），这些错误在本评差中会被一律计为线上缺陷。

### 2. 配对错误制造了假缺陷

| 证据 | 说明 |
|---|---|
| **29 家**本地记为 0 行，却评为本地“PASS”；同时线上被判“FAIL：行数异常偏多，多出 N 行” | 评差总表 |
| 例：青岛鼎信通讯消防安全有限公司——评差表记“原表 0 行、本地 0 行”，线上判“多出 515 行”；而本地成果目录中 `鼎信消防全系列产品-标准解析.xlsx` **实际有 515 行**，与线上行数相同 | `02_四位经办人分类完整档案/1_程雅洁（30家）/3_本地标准解析成果/` |
| 原因：本地文件按供应商目录名做模糊文件名匹配（`load_local_df`，第 36–46 行），文件名不同即配不上并记为 0 行；线上文件按名称前 6 个字匹配（第 75 行），存在错配风险 | `generate_evaluation_report_v2.py` |

因此 E02“多采/重复行”40 家中，至少这 29 家的判定无效；E15“整单遗漏”17 家中，有多少是配对失败所致也需重查。

### 3. 白皮书自相矛盾
- “本地自跑流水线完成度 100%（129 份全部完整还原）”与评差表中 29 家本地 0 行矛盾；且“完成度”不等于“准确度”。
- 本地输出本身存在错误却被评为 PASS。例：上述鼎信本地文件的“供应商名称”为“鼎信消防全系列产品”（由文件名推得），正确应为“青岛鼎信通讯消防安全有限公司”；“品牌”为“鼎信消防全系”。

## 三、重要问题

### 1. 比对方法会系统性制造假缺陷

| 问题 | 位置 | 后果 |
|---|---|---|
| 逐行比对按行序号（第 idx 行对第 idx 行），不做行对齐 | 第 256–317 行 | 只要漏一行、多一行或顺序不同，其后所有行错位，产生连锁的单价/单位“不符” |
| 单位做字符串完全相等比较 | 第 265 行 | `m²` 与 `㎡`、`米` 与 `m` 被判为单位错误 |
| 单价列：本地取“市场价”，线上取“市场价”或“单价”，未区分含税/不含税口径 | 第 235–236 行 | “混淆税率”类判定缺少明确规则 |
| 规格比较：本地取“规格参数”，线上取“厂家原始规格参数”，比较的不是同一字段；整表留空判定只看“厂家原始规格参数”，不看线上的属性列（品种、材质等） | 第 242、306–307 行 | 线上若把规格写在属性列，会被误判为规格丢失（已抽查安华一例：该例线上属性列也为空，判定成立；但其他例需复核） |
| 线上压缩包内所有 xlsx 的所有 Sheet 全部拼接计行 | 第 56–67、77–90 行 | 若包内含汇总/重复 Sheet，会被计为“多采” |
| 商务条款只看第一行“报价说明”的关键词 | 第 190–206 行 | 未确认线上系统当初是否收到报价说明图片；若未收到，E13 不属于解析缺陷 |

### 2. 技术描述与代码不符

| 白皮书表述 | 实际 |
|---|---|
| 置信度低于 0.95 或两模型不一致时触发交叉验证投票 | 代码中不存在 0.95 阈值与投票机制 |
| 行数守恒断言，不守恒则自动挂起报警 | 代码中不存在 |
| Gemini 3.8 Flash + DeepSeek 视觉交叉还原 | 本机调用 Gemini API 返回“地区不支持”，Vertex AI 返回 403；程序会静默回退到 DeepSeek，实际均为 DeepSeek 结果 |
| 单 Sheet，彻底关闭辅助 Sheet | 删除了“原表对账”“待复核说明”等留痕信息，削弱可审计性；与“证据链”的定位相悖 |
| 结果可供专家调阅查验 | 评差、批量运行等 14 个新脚本与 8 个已改文件均未提交版本库，结果对应不到确定的代码版本，无法复现 |

### 3. 口径与表述
- 仅有“整单合格率”一个指标，缺少字段级准确率与置信区间；E13 无具体数字（“普遍存在”）。
- E05“关键参数留空”、E07“混淆税率”需要事先写明判定规则。
- “四人分项成绩单”按经办人排名，实际反映的是各批文件难度不同，不是人的差异；在评审会上公开个人排名存在风险，也没有数据支撑这种归因。
- “绝对真值”“无可辩驳”“经得起任何现场抽检”“投行级”等绝对化措辞与证据强度不匹配，评审专家会据此重点找反例。

## 四、整改要求（提交评审前必须完成）

1. **人工核实真值子集**：分层抽样约 24 家（四批次、各文件类型都覆盖，含全部有争议者），只看原件人工转录，附证据截图；禁止使用任何模型或程序输出。
2. **先量本地程序的准确率**：在真值子集上测；本地达不到接近 100%，不得作为基准。
3. **三方裁决**：线上与本地每一处不一致都回到原件判定（线上错 / 本地错 / 两者都错 / 原件无法判定），**只有“线上错”计入线上缺陷**。
4. **修复评差脚本**：显式配对表、行对齐、单位归一、单价口径规则、规格字段对齐、本地也要被评、去掉写死的 PASS。
5. **重算并规范报告**：整单合格率 + 字段级准确率 + 95% 置信区间；在抽样裁决基础上外推全量时注明方法与不确定度。
6. **白皮书修订**：技术描述与代码一致；写明代码版本号；去掉个人排名，改按文件类型与难度分组；去掉绝对化措辞；增加“局限性”章节。
